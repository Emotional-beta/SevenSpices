# 《七荤八素》程序架构设计文档

> 版本：v0.1
> 项目类型：2D 独立游戏
> 技术栈：Godot 4.7.2 .NET + C#
> 开发环境：Windows 10
> 编程工具：Claude Code
> 版本管理：Git + GitHub
> 文档状态：核心架构确定版

---

# 一、架构目标

《七荤八素》采用**核心逻辑与表现层彻底分离**的架构。

主要目标：

1. 核心游戏逻辑不依赖 Godot UI。
2. 核心规则可以脱离 UI 进行自动化测试。
3. 食材、食客、道具、伙伴等内容采用数据驱动。
4. 新增游戏内容时，尽量不修改核心系统。
5. 效果系统能够支持复杂的连锁触发。
6. 游戏状态集中管理。
7. 普通锅、最终锅尽量复用同一套核心逻辑。
8. 为后续大量增加食材、道具、伙伴、食客和效果保留扩展空间。
9. 避免为了未来需求过早引入不必要的复杂架构。

---

# 二、总体架构

项目采用四层结构：

```text
┌─────────────────────────────┐
│        Presentation         │
│      UI / 动画 / 音效       │
├─────────────────────────────┤
│         Game Layer          │
│   游戏流程 / 状态机 / 场景   │
├─────────────────────────────┤
│        Domain Layer         │
│   游戏规则 / 状态 / 效果     │
├─────────────────────────────┤
│         Data Layer          │
│ 食材 / 食客 / 道具 / 伙伴数据 │
└─────────────────────────────┘
```

核心依赖原则：

> **低层不能依赖高层。**

尤其是 Domain / Core 层不得直接依赖 Presentation 层。

例如：

```text
Ingredient
```

不得直接操作：

```text
Label
Button
AnimationPlayer
Control
Node2D
```

食材只负责描述自身规则和产生效果。

# 五、GameState

`GameState` 保存当前游戏的重要状态。

主要职责：

* 保存游戏状态。
* 提供其他系统访问当前状态的入口。
* 作为存档系统的重要数据来源。

`GameState` **不负责执行复杂游戏流程**。

例如：

```text
GameState
    Gold = 100
```

金币增加的具体规则由对应的游戏系统执行，而不是由 `GameState` 自己承担整个流程。

## 6.2 IngredientBasket

玩家当前拥有的食材实例。

## 6.3 Items

玩家当前拥有的道具。

## 6.4 Companions

玩家当前拥有的伙伴。

# 七、食材系统

食材必须拆分为两个概念：

```text
IngredientDefinition
IngredientInstance
```

---

## 7.1 IngredientDefinition

表示：

> "这种食材是什么？"

它属于静态定义数据。

例如：

```text
ID
Name
Rarity
BaseScore
Flavor
Effects
```

示例：

```text
ID: rice
Name: 米饭
Rarity: Common
BaseScore: 5
Flavor: None
Effects: [...]
```

`IngredientDefinition` 不代表某一份实际存在的食材。

---

## 7.2 IngredientInstance

表示：

> "玩家当前拥有或食材池中的这一份具体食材。"

例如：

```text
InstanceID: 001
DefinitionID: rice
```

因此：

```text
米饭①
米饭②
米饭③
```

都是不同的：

```text
IngredientInstance
```

但引用相同的：

```text
IngredientDefinition
```

---

# 八、为什么必须区分 Definition / Instance

游戏未来可能出现：

* 修改某一份指定食材。
* 摧毁某一份指定食材。
* 给某一份食材附加临时状态。
* 根据某一份食材的来源进行判断。
* 记录某一份食材是否已经被触发。

因此不能只保存：

```text
rice
rice
rice
```

而必须能够区分：

```text
rice_001
rice_002
rice_003
```

---

# 九、食材池

建立：

```text
IngredientPool
```

负责管理当前可以被抽取的食材实例。

主要职责：

* 保存当前可抽取实例。
* 随机抽取。
* 无放回抽取。
* 最多抽取 3 个。
* 如果不足 3 个，则全部抽出。
* 玩家选择的实例从池中移除。
* 未选择的实例继续存在。

基本流程：

```text
IngredientPool
      │
      ▼
Draw(3)
      │
      ▼
Candidate[]
      │
      ▼
Player Choose
      │
      ├── Selected → Remove
      │
      └── Others → Return
```

---

# 十、效果系统

效果系统是整个项目的核心系统之一。

建立：

```text
Effect
EffectContext
EffectSystem
```

效果可以包括：

```text
AddScoreEffect
AddFlavorEffect
MultiplyScoreEffect
FreezeEffect
ExplodeEffect
DoubleNextEffect
ModifyIngredientEffect
```

实际效果类型以后可以继续扩展。

核心原则：

> 新增效果不应该要求修改锅系统的核心流程。

---

# 十一、Effect

`Effect` 是所有游戏效果的统一抽象。

效果负责描述：

> "发生了什么规则变化。"

而不是负责：

> "整个游戏流程应该怎么运行。"

例如：

```text
AddScoreEffect
```

负责增加分数。

而：

```text
PotController
```

负责决定什么时候进入效果结算阶段。

---

# 十二、EffectContext

每一次完整效果链都有自己的：

```text
EffectContext
```

主要用于记录当前效果链的上下文。

至少包含：

```text
ChainID
CurrentBowl
CurrentIngredient
TriggeredSources
TriggeredEffects
GameState
PotState
```

其中：

### ChainID

当前效果链的唯一标识。

### CurrentBowl

当前正在处理的碗。

### CurrentIngredient

当前正在处理的食材。

### TriggeredSources

本次效果链已经触发过的来源。

### TriggeredEffects

本次效果链已经执行过的效果。

### GameState

当前游戏状态。

### PotState

当前锅状态。

---

# 十三、效果链与循环保护

效果系统必须防止无限递归。

例如：

```text
A
↓
B
↓
C
↓
A
```

如果 A 已经在当前 `ChainID` 中触发过，则不能再次无限触发 A。

规则：

> 同一个 EffectContext 中，同一个触发源不得无限重复触发。

下一次加入食材时必须创建新的：

```text
EffectContext
ChainID
```

因此：

```text
第一次加入食材
    ↓
ChainID = A

第二次加入食材
    ↓
ChainID = B
```

A 在新的效果链中可以重新触发。

---

# 十四、食材与效果系统的关系

禁止让具体食材直接控制整个游戏系统。

错误方式：

```text
Rice
├── 修改锅
├── 修改玩家
├── 修改 UI
├── 修改食客
└── 修改金币
```

正确方式：

```text
Ingredient
    ↓
产生 Effect
    ↓
EffectSystem
    ↓
修改 GameState / PotState
```

这样可以让食材内容与核心系统解耦。

例如：

```text

├── BowlLimit
├── Ingredients
├── Flavors
├── BaseScore
```

## 15.2 PotController

负责一锅的流程。

基本流程：

```text
StartPot
    ↓
StartBowl
    ↓
DrawIngredients
    ↓
PlayerChoose
    ↓
UseItems
    ↓
AddIngredient
    ↓

    ↓

    ↓

    ↓
```

普通锅和最终锅尽量使用同一套核心逻辑。

# 十六、碗状态机

每一碗必须拥有明确的状态。

建议：

```text
Start
↓
Customer
↓
ItemPhase
↓
IngredientSelection
↓
IngredientResolve
↓
ScoreCalculation
↓
ScoreLocked
↓
Serving
↓
Reward
↓
End
```

状态机的主要作用是：

> 防止玩家在不允许操作的阶段执行非法操作。

例如：

```text
ScoreLocked
```

之后不能再次加入食材。

---

# 十七、分数系统

建立：

```text
ScoreCalculator
```

所有最终分数计算应该集中处理。

不要把最终分数计算散落在各种食材代码中。

基本流程：

```text
基础状态
 ↓
味道
 ↓
道具
 ↓
食材效果
 ↓
其他规则
 ↓
最终基础分
 ↓
倍率
 ↓
FinalScore
 ↓
Lock
```

核心规则：

> 分数必须完成完整效果结算后才能锁定。

---

# 十八、倍率系统

倍率是独立的规则数据。

默认倍率：

```text
1  → ×1
2  → ×1
3  → ×1
4  → ×1
5  → ×1
6  → ×2
7  → ×4
8  → ×8
9  → ×16
10 → ×32
```

不要在多个系统中散落：

```csharp
if (bowl == 6)
```

这样的硬编码。

如果未来伙伴或其他机制可以修改倍率，应通过倍率系统、Modifier 或其他统一规则机制完成。

---

# 十九、锅底系统

建立：

```text
BottomState
BottomExtractor
```

锅底必须被视为：

> **状态。**

而不是一个在最终结算时偷偷增加的 Bonus。

---

## 19.1 锅底生成

本锅结束：

```text
CurrentPotFinalState
        ↓
BottomExtractor
        ↓
30%
        ↓
Floor
        ↓
Minimum 1
        ↓
BottomState
```

边界：

- 本锅最终为 0 的味道不写入锅底（旧锅底保持不变）；
- 锅底单调不减：提炼结果与旧锅底取较大值写入。

---

## 19.2 新锅应用

新锅开始：

```text
BottomState
      ↓
ApplyToPot
      ↓
PotState
```

例如：

```text
BottomState:
Sweet = 6
```

开锅后：

```text
PotState.Flavor.Sweet = 6
```

之后这 6 点甜味与本锅正常产生的甜味没有本质区别。

---

## 19.3 锅底衰减

锅底进入下一锅后：

> 不允许因为进入下一锅而再次自动进行 30% 衰减。

30% 衰减只发生在规定的锅底提取阶段。

---

# 二十、食客系统

拆分为：

```text
CustomerDefinition
CustomerInstance
CustomerSystem
```

---

## 20.1 CustomerDefinition

描述一种食客的静态规则。

例如：

```text
ID
Name
Type
Reward
SatisfactionCondition
```

---

## 20.2 CustomerInstance

表示实际出现在当前游戏流程中的具体食客。

---

## 20.3 满意条件

稀有食客可以具有类似：

```text
Score >= X
```

或者：

```text
Flavor >= Y
```

等条件。

满足条件：

```text
Satisfied = true
```

然后执行对应奖励：

```text
DropIngredients()
DropItems()
AddToCompanionCandidates()
```

具体奖励规则由游戏设计文档决定。

# 二十一、伙伴系统

建立：

```text

CompanionInstance
CompanionSystem
```

伙伴效果不应该直接硬编码到：

```text

```

优先通过：

```text

Modifier
Event

```

参与游戏。

伙伴的核心定位是：

> 改变游戏规则，而不仅仅是增加数字。

# 二十二、事件系统

建立轻量事件系统：

```text
GameEvent
```

初步事件：

```text
PotStarted
BowlStarted
IngredientDrawn
IngredientAdded
EffectTriggered
ScoreCalculated
ScoreLocked
CustomerServed
CustomerSatisfied

CompanionAdded
```

事件系统用于降低模块之间的直接依赖。

例如：

```text

```

可以被伙伴系统监听。

```text

```

可以被食客系统监听。

```text

```

可以被 UI 监听。

核心系统不应该为了通知 UI 而直接寻找 UI Node。

# 二十三、UI 与表现层

UI 只负责：

> **显示状态 + 发送玩家输入。**

例如：

```text
IngredientCard
```

负责显示：

```text
名称
稀有度
分数
味道
效果
```

玩家点击后：

```text
GameController.SelectIngredient(instanceId)
```

UI 不应该自行修改核心游戏状态。

表现层包括：

```text
UI
Animation
Audio
VFX
```

均属于 Presentation 层。

---

# 二十四、数据层

第一版优先使用：

> Godot Resource / C# 数据类

而不是一开始就使用 JSON、数据库等复杂方案。

例如：

```text
IngredientDefinition
CustomerDefinition
ItemDefinition
CompanionDefinition
```

通过数据资源保存。

这样 Godot 编辑器可以直接编辑内容。

未来如果内容规模达到数百甚至更多，再根据实际需求评估 JSON、CSV 或其他数据方案。

# 二十八、架构扩展原则

未来增加食材、道具、伙伴、食客或效果时：

优先选择：

```text
新增 Definition
+
新增 Effect
+
新增配置
```

而不是：

```text
修改 PotController
+
修改 ScoreCalculator
+
增加大量 if/else
```

理想状态：

> 新增内容主要增加数据，而不是增加核心系统中的特殊判断。

但如果新的游戏机制确实要求修改核心架构，应先确认机制需求，再修改核心系统。

# 三十、最终架构原则

本项目始终遵循以下原则：

1. 核心逻辑与表现层分离。
2. Domain / Core 不直接依赖 UI。
3. 游戏状态集中管理。
4. 食材必须区分 Definition 和 Instance。
5. 食材通过 Effect 参与游戏规则。
6. EffectSystem 负责效果执行。
7. EffectContext 负责效果链上下文。
8. 同一 EffectContext 内禁止效果无限循环。
9. 每次新的效果链必须创建新的 ChainID。
10. 分数必须在完整效果结算后才能锁定。
11. 倍率在最终基础分计算完成后应用。
12. 锅底是状态，不是临时 Bonus。
13. 锅底在新锅开始时直接应用到 PotState。
14. 锅底不会因为进入下一锅而重复衰减。
15. 普通锅与最终锅尽量复用核心逻辑。
16. 内容优先采用数据驱动。
17. 避免大量 if/else 硬编码具体内容。
18. 核心规则必须有自动化测试。
19. 不为了未来可能需求引入不必要的复杂架构。
20. 如果程序实现与游戏设计发生冲突，必须先确认规则，而不是擅自修改。

# 三十二、味道系统（架构预留）

本节记录为支持「味道系统」（见游戏设计文档 §十一）所需的最小架构约定。

## 32.1 FlavorType 扩展

味道枚举由 5 种扩展为 7 种：酸、甜、苦、辣、鲜、咸、麻。

新增味道**追加在枚举末尾**，不改变既有声明顺序（并列取舍、结算顺序均依赖声明顺序的确定性）。

## 32.2 味道互动层

锅系统（§十五）在「加料 → 效果结算」之间，插入**味道互动层**：

1. 物理状态检查
2. 味道动词结算（按枚举声明顺序）
3. 麻的共振

味道互动**在加料瞬间结算**。

新增味道动词应通过 Effect / 数据配置参与，而不是在 PotController 中写特例。

## 32.3 味道分

分数系统（§十七）的基础分新增「味道分」分量：

> 基础分 = 食材基础分 + 味道分 + 其他效果分
> 味道分 = Σ（各味道值 × 1 × 其他效果加成）

## 32.4 跨碗状态：陈酿池

「苦·陈酿」需要一个新的**跨碗状态（陈酿池）**，模式与现有 `TotalBaseScore` 一致：随锅存活、随碗不重置、随锅重置。

该状态**必须纳入预览快照（PotStateSnapshot）**，否则悬停预测会与真实结算不一致。

存入与复利在同一加料内一并结算：`AgingVerb.Apply` 先按比例存入，随后 `AgingVerb.AdvanceCycle` 对**含本次存入**的池整体复利，因此本次存入当次即计入复利（设计文档 §11.2）。

## 32.5 物理状态容器

物理状态（如「臭」）使用通用、数据驱动的**锅内状态容器**承载，而不是为单个状态写死字段，以便后续纯数据扩展。

「臭」的锅末「现实转移」复用现有「锅底提炼后结算钩子」（同 `IBottomSettlementHook` 模式，在 `PotController.ClosePot` 提炼之后执行），只写 BottomState、不改 PotState。

## 32.6 最终锅

最终锅内「陈酿池」立即全额兑现；「臭」的锅末转移照常执行。
